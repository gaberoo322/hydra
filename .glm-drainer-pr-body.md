Port the #3729 per-item verdict-stability guard from `sweep_target` to `sweep_orch`.

`needs_triage_orch` is a coarse presence boolean (needs-triage count on the
orch board > 0). `sweep_orch` re-fires on it every 15 min (900 s class cooldown)
forever against permanently-parked standing-recheck-trigger items — e.g. #3921,
which carries `needs-triage` indefinitely by design — burning ~200–300 K
tokens/hour re-confirming the same verdict. `needs_triage_orch` has no per-item
eligibility gate, so nothing ever tells sweep "you already looked at that one."

The fix mirrors `sweep_target` (#3729) exactly: `collect-state.sh` emits the
current orch needs-triage item-number set as a fresh per-turn fact
(`orch_needs_triage_items`), and `decide.py` keeps a per-item stamp map
(`state.orch_triage_item_stamps`). `sweep_orch` fires iff ≥1 item in the current
set has no stamp or a stamp older than `ORCH_TRIAGE_BACKOFF_SEC` (6 h default,
independently env-overridable via `HYDRA_ORCH_TRIAGE_BACKOFF_SEC`); on fire,
every item in the CURRENT set is stamped (uniform lane-clock reset) and departed
items are pruned. The four guard helpers are SHARED (parameterized by signal
name / state key / backoff constant), not forked into `orch_` duplicates. The
900 s class cooldown stays a necessary, independent AND-composed condition.

The one structural delta from #3729: `sweep_orch` has a second OR-composed
trigger (`untriaged_orphans_orch`) that `sweep_target` lacks. When every current
needs-triage item is inside its backoff window, the `needs_triage_orch` branch is
suppressed but control FALLS THROUGH to the orphan check (it does not `return
None`) — the guard must never drop a live orphan-routing opportunity.

## Friction Report

One real defect surfaced and fixed during the work, none outstanding.

- **collect-state.sh jq filter tripped the `active_dev_orch` test (FIXED).**
  The first orch-collector draft used `--jq '[.[].number] | sort | …'`. The
  `extractJqFilter()` regex in `test/autopilot-dev-orch-gate.test.mts`
  (`/--jq '(\[[\s\S]*?\] \| length)'/`) non-greedily matches the first same-line
  `[...]` after `--jq '`; placing the orch collector's `[` before the
  `active_dev_orch` collector made the match span to the wrong `] | length'`,
  extracting a garbage filter and breaking 1 of that suite's 16 cases. Rewrote
  the jq to `map(.number) | sort | map(tostring) | join(" ")` (no leading `[`,
  idiomatic, output-identical). Verified all 16 collect-state/active_dev_orch
  tests pass and the live `gh issue list` emit is unchanged
  (`orch_needs_triage_items=3815 3921 3953`). This was the only real failure; the
  other `npm test` failures in the first run were the documented
  concurrency/shared-Redis flakes (at `--test-concurrency=1` via `npm run
  test:debug`, only this one case was red).
- **Single-line literal constraint for the reconciliation gate.** Two helper
  signatures in `decide.py` (`_triage_item_set`, and the `sweep_orch`
  `_stamp_triage_items` call) were initially split across lines by Black's 88-col
  rule, so a single-line `file-contains:` literal could not match them verbatim.
  Collapsed the `sweep_orch` stamp call to one line (still 80 cols, readable);
  for the split `_triage_item_set` signature I instead pointed INV-13 at the
  single-line `_triage_stamps` signature (equally valid purity proof) rather than
  reformat a signature Black would just re-split. All 13 assertions verified
  present/true at HEAD.
- No out-of-scope files touched. The added changelog fragment
  (`.changelog/3939-sweep-orch-triage-backoff.md`) follows the repo convention
  and is not in the issue's scope list; it is a release-note artifact, not a
  source change.
