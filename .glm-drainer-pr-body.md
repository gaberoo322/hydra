## Roll the Weekly Reset Anchor forward on the admission path so the Pacing Curve ramps

The admission path (`getEligibilityUsage` → `projectEligibility`) served the **raw** Weekly Reset Anchor seed from the env var instead of its **projected** current-window boundary. Per CONTEXT.md:217 the Weekly Reset Anchor is "projected forward in 7-day multiples"; serving the 8-week-old seed meant the Pacing Curve's `targetPercent` was pinned at the Pacing Ceiling (92) at *every* instant, so `paceState` could never reach `"ahead"` — the curve was inert by construction, degenerating into a restatement of the 90% hard stop.

This PR projects the anchor forward via the existing `projectResetWindow(seedMs, nowMs).currentMs` (token-math.ts) on the admission path, and guards `projectPacingCurve` so a non-OAuth (`estimate`) source — the `unavailable()` zeros — stays neutral instead of being consumed as a real 0% burn. With the roll, `targetPercent` is a genuine ramp: ~1.6 early-window, ~91.4 late-window, and a 50% burn reads `"ahead"` (below the 90% weekly stop) — the previously-unreachable verdict.

This PR implements the live, operator-approved policy (#3804) and does **not** reverse it (that would be a Tier-0 / operator decision). 8 of 9 invariants are discharged honestly below; INV-6 cannot be — no machine assertion can prove "outage does not flip allow to false" because the shipped code intentionally flips it.
