# Salvage audit: what CSB reuses from hydra-betting

Resolves #4321. Read-only sweep of `/home/gabe/hydra-betting` (app code root `web/src`) to decide what carries over to **CSB (Claw Street Bets)** — the new autonomous intraday crypto trading system: one venue adapter, an OWNED fill simulation shared across backtest/paper/live, TS + Next.js + Postgres + systemd, app scaffolded at the repo root (reversing betting's `web/` subdir layout), and five risk invariants (server-side stops on every entry, per-trade risk %, daily loss halt, dead-man's switch, credential fence). CSB is scaffolded fresh; nothing here is copied verbatim without a stated adaptation.

Verdict legend: **REUSE-AS-IS** (pattern/convention ports directly, rename only) · **ADAPT** (structure is right, content is betting-specific and needs rework) · **DO-NOT-CARRY** (retired, dormant, or arbitrage/cross-venue-specific — no CSB equivalent).

## 1. Venue/provider adapter seam

hydra-betting has **no formal `Venue` TypeScript interface** — "adapter" is a directory convention, not a type contract. Each venue gets its own directory under `web/src/lib/providers/<name>/` split into auth / rate-limiter / normalization / errors / client-factory submodules, and a separate per-venue **executor** (`web/src/lib/execution/kalshi-executor.ts`, `polymarket-executor.ts`) that writes to the one shared `venue_orders` table. `web/src/lib/providers/CONTEXT.md` codifies the **Venue** (order-submittable) vs **MarketDataSource** (read-only signal feed) distinction and states the foundational rule: adapters are never deleted even with zero callers (CLAUDE.md rule #1).

| Item | Verdict | Rationale |

## 2. Execution guardrails → CSB's five risk invariants

This is the strongest reuse area. hydra-betting's single-leg **directional** execution path (M13, the survivor of the ADR-0002 cross-venue-arbitrage retirement) is architecturally close to what CSB needs: one venue, one leg, explicit fail-closed gates composed in front of a submit call.

| Dual-leg / cross-venue arbitrage machinery: `execute-arbitrage-shared-types.ts`, `execution-pair-lock*.ts`, `settlement-criteria-preflight` (cross-venue resolution-criteria equivalence), RFQ (`kalshi-rfq.ts`), `sequential-dual-leg-*` timeout/SLA | **DO-NOT-CARRY** | — | All ADR-0002-retired or exclusively cross-venue-pair concepts (pair locking, dual-leg approval envelopes, RFQ handoff). No single-venue crypto analogue. |

**Gap worth flagging explicitly:** CSB's brief calls for an **OWNED fill simulation shared across backtest/paper/live**. hydra-betting does **not** have this — its "paper mode" (`directional-single-leg-persist.ts`) synthesizes a fully-filled receipt at the planned price with zero slippage/partial-fill/fee model by construction (`requestedCount === filledCount`, fees zero, status resolves straight to `executed`). This is explicitly documented as a simplification ("paper has no partial-fill / slippage / fee model"), not a real simulator. **Nothing in hydra-betting satisfies CSB's fill-simulation requirement — it must be built new**, not adapted from this codebase.
