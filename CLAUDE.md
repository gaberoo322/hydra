# Hydra Orchestrator

Autonomous software-building framework. The **Orchestrator** is a control plane for **Claude Code subagents** (`hydra-dev` for orchestrator work, `hydra-target-build` for target work) dispatched in parallel by **`hydra-autopilot`**. State lives in Redis; configs are git-tracked under `~/hydra/config/`. Hard verification (`npm test`, `tsc`, build) is deterministic — never an agent claim.

> Terms in **bold** are defined in [`CONTEXT.md`](./CONTEXT.md). Use them exactly.

## Architecture (one paragraph)

`hydra-autopilot` is a long-running decision loop: a single Claude Code session dispatches background subagents in parallel — one per **class** — under per-class cooldowns and a token budget (full taxonomy in the autopilot playbook). Each code-writing class runs in a fresh `git worktree` and opens a PR; **CI is the merge gate**, never an in-cycle check. The orchestrator HTTP service (port 4000) is the **data plane**: Redis state, event bus (`hydra:*` streams), the observability heartbeat (`src/scheduler/heartbeat.ts`), the dashboard + REST API, and the tier classifier (`src/tier-classifier.ts`). The **Pre-merge Gate** itself is CI jobs + branch protection, not an in-process module — `src/gate.ts` was removed with the codex control loop. It no longer runs a self-driving control loop (see [ADR-0006](./docs/adr/0006-codex-cli-removed-autopilot-only.md), [ADR-0012](./docs/adr/0012-autopilot-is-the-single-brain.md)).

## Coding Conventions

- **TypeScript** (`.ts`, import/export). Source in `src/`, tests in `test/*.test.mts`.
- **Node is pinned** via `.nvmrc` (exact version) + `package.json`'s `engines.node` range, enforced by `test/toolchain-pin.test.mts` — a failure there means the runner has drifted, so `nvm use` against `.nvmrc` rather than "fixing" the symptom (the `--experimental-strip-types` runner behaviour is coupled to the Node minor).
- **Runtime deps are operator-approved only** (ADR-0005): `express`, `ioredis`, `ws`, `@sentry/node`, `zod`, `pino`. Node stdlib for everything else. (`pino` is the structured logger seam — import `logger` from `src/logger.ts`, never `pino()` directly; ADR-0027.)
- **Never throw from merge/grounding/verification** — return result objects so callers decide how to report failures.
- **Fail loud**: every `catch` either logs `console.error` with context or is annotated `/* intentional: reason */`. Silent catches caused every major 2026-04 incident.
- **Typed errors carry a machine-readable `code`** (#756) — for exceptional `throw` sites prefer a subclass from `src/errors.ts` (e.g. `InvalidArgumentError`, `RedisSeamError`) over a bare `Error`; callers/tests discriminate on `err.code`, not `err.message`. Migration is opportunistic.
- **Redis access through `src/redis/<domain>.ts` typed accessors** — never `new Redis()` directly; never import `redis/keys` or `redis/kv` from outside `src/redis/`. See **Redis Adapters** in `CONTEXT.md`; enforced by `scripts/ci/redis-seam-check.ts`.
- **HTTP request bodies validate through `src/schemas/<domain>.ts`** (zod `safeParse`; on failure return 400 `{code:"schema-validation-failed", issues}`). The schema is the source of truth for both the parser and the inferred type. See **Schemas** in `CONTEXT.md`.
- **API routes in sub-routers** — `src/api.ts` is a thin mount point; handlers live in `src/api/<domain>.ts` (factory functions receiving `eventBus` if needed). `eventBus` is a parameter, never a module global.
- **`grounding.ts` is read-only** — never mutate the workspace from inside grounding.
- **Structural code search** — for call-site / AST questions ("find every caller of `moveItemToLane`", "every `new Redis(...)`") prefer `npm run ast-search -- --pattern '<ast-grep pattern>'` (`scripts/ast-search.ts`, tool-scout #1797) over text `grep`: it matches *syntax*, so it never false-matches a comment or string literal. Reusable AST-exact lint rules live as YAML under `src/ast-grep-rules/` and run in the advisory `ast-grep-lint` workflow (a Tier-3 sibling, NOT in `ci.yml`); add a sibling file to add a rule. ast-grep is invoked via `npx`, deliberately not a package.json dependency (keeps it off the ADR-0005 runtime-dep allowlist and the lavamoat allow-scripts gate). **Lane boundary:** ast-grep owns TypeScript (it has a TS tree-sitter grammar wired here); for the non-TS long tail — YAML / shell / Markdown under `.github/`, `config/`, `scripts/` — reach for **comby** (`comby.dev`) instead, whose `:[hole]` template matches a balanced expression in any language. Comby rules live as `.toml` under `scripts/comby-rules/` and run in the advisory `comby-check` workflow (another Tier-3 sibling, NOT in `ci.yml`); comby is a pinned pre-built binary downloaded in CI (no npm distribution), same ADR-0005 / allow-scripts rationale as ast-grep. **Third lane — fuzzy block search:** when you *don't yet know* the exact identifier or AST shape ("where is the tier classifier wired?", "find the retry logic"), use `npm run probe-search -- --query '<words>'` (`scripts/probe-search.ts`, tool-scout #1799) — probe (probelabs) combines ripgrep speed with tree-sitter parsing and BM25 ranking to return whole, relevance-ranked code *blocks* across any language with zero indexing. **Search is TWO lanes, not three:** use ast-search for EXACT syntax and probe-search for FUZZY relevance. The former third lane — **OpenViking for SEMANTIC similarity over accumulated knowledge — is RETIRED** (ADR-0033); there is no semantic-search backend, so a question that used to route there now routes to probe-search. Same pinned-`npx`, no-dependency lane as ast-grep/comby/promptfoo. The higher-leverage probe MCP-server path is an operator decision (out of scope of #1799).
- **Evals (agent/prompt behavior)** — to A/B-test a skill or agent-class prompt against a golden-task set, use **promptfoo** (`npm run eval`, configs under `evals/`); the advisory `eval-gate` workflow runs it on PRs (Tier-3 sibling, NOT in `ci.yml`; same pinned-`npx`, no-dependency lane as ast-grep/comby). The first eval is offline (no API key); live-provider CI is an operator-gated follow-up. For a numeric **TypeScript** scorer (e.g. "does this PR close the right issue? 0/1"), write a `file://scorers/<name>.ts` assertion (seed: `evals/scorers/issue-ref.ts` via `npm run eval:ts`) — promptfoo runs it through its own esbuild loader, so it stays on the no-dependency lane (evalite was scouted in #1803 and declined: it hard-requires a vitest devDep that trips the allow-scripts gate — promptfoo already covers the niche). Full contract: [`docs/evals.md`](./docs/evals.md).
- **Dependency hygiene** — to audit runtime-dep staleness, use `npm run deps:check` (runtime deps only) or `npm run deps:check:all` (all deps). Both invoke `npx taze@19 --json` (tool-scout #3641), which returns a machine-readable schema per package: `{name, currentVersion, targetVersion, diff, update, currentVersionTime, targetVersionTime}`. The `diff` field (`patch`/`minor`/`major`) lets agents apply a policy without string-parsing. Runs via pinned `npx taze@19` — no `package.json` devDep entry, same no-dependency lane as ast-grep/comby (ADR-0005). Write mode (`taze minor`) requires operator confirmation; use scan-only mode autonomously. An advisory weekly CI workflow (`.github/workflows/deps-check.yml`) runs `deps:check` and uploads a JSON artifact.
- **Vulnerability scanning (OSV)** — to scan lockfiles for known CVEs beyond what the required `npm audit` gate sees, run `bash scripts/osv-scan.sh` (tool-scout #3642). It downloads the pinned `osv-scanner` binary (Google's OSV scanner), verifies its SHA256, and emits stable machine-readable JSON with OSV IDs: `{results: [{packages: [{package: {name, version, ecosystem}, vulnerabilities: [{id, aliases}], groups: [{ids, fix_info: {fixed_version}}]}]}]}`. The IDs (`GHSA-*`/`CVE-*`) are stable and parseable without LLM interpretation — an agent can file targeted bump issues from them. **This complements, never replaces, `npm audit`**: `npm audit` is a REQUIRED check querying only the npm advisory registry (a new CVE there reddens the merge queue repo-wide with zero code change — the poison-pill class in operator memory `reference_npm_audit_required_check_ambient_poison_pill`); OSV aggregates GitHub Advisory + NVD + OSS-Fuzz, so this advisory scan can surface a CVE *before* it hits npm advisory and wedges auto-merge. **Scan-only** — the wrapper never runs `osv-scanner fix` (which rewrites `package-lock.json` destructively); that is an operator-confirmed action. Runs via a pinned pre-built binary with SHA256 verification — no `package.json` entry, no install scripts, same no-dependency lane as the comby binary (ADR-0005). An advisory CI workflow (`.github/workflows/osv-scan.yml`, a Tier-3 sibling NOT in `ci.yml`) runs it on PR + weekly cron and uploads `osv-results.json` as an artifact.

## CI/CD & Deployment

- **All changes to master go through a PR.** Branch protection enforces CI. **Agents: always work on a feature branch; never push directly to master.**
- **Always run `npm test` before committing.**
- **CI** (`.github/workflows/ci.yml`): typecheck + test, dashboard build, tier-gate, mutation kill-rate + scope-enforcement (see [`docs/quality-gates.md`](./docs/quality-gates.md)).
- **Deploy** runs automatically on merge to master (self-hosted runner). **Never deploy by restarting the service without building the dashboard first** — Express serves `dashboard/dist/`, so stale builds mean stale UI. Full deploy steps + emergency manual deploy: [`docs/reference.md`](./docs/reference.md).
- **Back-to-back master merges cancel the older commit's `deploy` job**: `ci.yml`'s concurrency group keys on `refs/heads/master`, so two pushes to master in quick succession land in the same group and `cancel-in-progress` kills the older run *including its `deploy` job* (the comment's "master unaffected" holds only vs PR refs). It self-heals at the tail — the last uncancelled master run deploys cumulatively — **unless** that tail run is itself cancelled or its needs-jobs flake, leaving master silently ahead of prod with **no alarm** (the watchdog checks health, not SHA drift); the single self-hosted runner makes an autopilot merge wave worse by serializing CI + deploys. **Mitigation:** after the LAST merge of a batch settles (no pending CI/merges), run `bash scripts/deploy.sh` once to deterministically bring prod to latest master — don't deploy mid-wave (it races the queued CI deploy). Proper fixes are Tier-0 (guard `cancel-in-progress` to non-master refs; add a deployed-SHA-vs-`origin/master` drift check to the watchdog).

## Self-Modification: Verifier Core & Tiers

Every PR is classified by blast radius on the monotonic ladder T1 (shallowest) → T4 (deepest), regardless of who proposed it ([ADR-0004](./docs/adr/0004-self-modification-tiers.md) + ADR-0015) — required verification depth ascends with the tier. The **Verifier Core** path list lives in `src/untouchable.ts` (`VERIFIER_CORE_PATHS` / `isVerifierCore`; [ADR-0001](./docs/adr/0001-untouchable-core-and-gate-extraction.md) + ADR-0015 — "Untouchable Core" is the retired name). **Never bypass the gate.** Operator escalation is the closed list in [ADR-0005](./docs/adr/0005-operator-escalation-is-narrow.md) (credentials/secrets, external-account actions, T4 / Verifier-Core changes, vision conflicts) — everything else Hydra researches and tries autonomously. Full tier table + path lists: [`docs/reference.md`](./docs/reference.md).

Tier names verification *depth*, not merge authority (ADR-0015, #742). Every PR auto-merges once it passes the verification depth required for its tier; the only route to the operator is an exhausted Deep-QA Remediation Loop on T4 (a 2nd failed deep-QA pass, #740).

| Tier | Scope | Required verification depth |
|------|-------|-----------|
| T1 — Prompt-shaped | Lesson files, prompt-only tweaks (`config/agents/`, `config/feedback/`) | QA PASS → auto-merge |
| T2 — Skill / verification | Skills under `~/.claude/skills/`, dashboard, `src/anchor-selection/` | QA PASS + **Outcome Holdback** → auto-merge |
| T3 — Core `src/` + demoted infra | Everything else in `src/`, plus `src/grounding.ts`, `src/cost/`, watchdog scripts, `scripts/deploy.sh` | QA PASS → auto-merge |
| T4 — Verifier Core | `.github/workflows/ci.yml`, `.github/workflows/deploy.yml`, `.github/workflows/deep-qa-gate.yml` (ADR-0020), `scripts/tier-classify.ts`, `src/tier-classifier.ts`, `src/untouchable.ts` | Deep-QA pass (#740); operator only via exhausted remediation loop |

## Common Pitfalls

- **Port 4000 conflict**: running `npx tsx src/index.ts` while the service is up trips the port guard. Check `lsof -ti:4000` first; `systemctl --user restart hydra-orchestrator.service` is the safe restart after a crash leaves the port held.
- **Worktree isolation**: every code-writing dispatch (`hydra-dev`, `hydra-target-build`) MUST run in a fresh `git worktree` — the harness aborts if cwd is the main working tree (`/home/gabe/hydra` or `/home/gabe/hydra-betting`). Abort rather than falling back to the main repo.
- **Kanban title matching**: use `anchor.reference`, not `task.title`, when calling `backlog.ts` functions — subagent-generated titles don't always match Kanban rows.
- **zsh `$status` is read-only**: never name a shell loop/poll variable `status` — zsh aliases `$status` to `$?`, so the assignment fails and the script exits 1 (bites Monitor/CI-poll loops). Use `st` / `run_state` instead.
- **`pgrep -f "<pattern>"` / `pkill -f` match the *caller's own* command line — an `until ! pgrep -f …` wait never exits, and `pkill -f` kills your own shell**: a one-liner that waits on (or kills) a process by name necessarily *contains* that name, and the `-f` form matches the full command line of every process — including the `zsh -c` running the loop. So `until ! pgrep -f "test-force-exit"; do sleep 45; done` finds itself, concludes the runner is still alive, and spins forever (three such shells sat ~11h in one session). The trap is silent: no error, negligible CPU, and the loop reads as correct. Measured directly — with **no** matching process alive, `pgrep -f "sentinel-…"` still returned a PID: its own. The `pkill -f` variant is worse: it terminates the shell issuing it (observed as a bare `exit 144` with the cleanup step's output truncated). **Fix:** break the self-match with a bracketed character class — `pgrep -f "[t]est-force-exit"` — which matches a real process's cmdline but not the literal pattern text sitting in the caller's own; verified in-repo that the bracketed form still finds the genuine process while dropping the self-match. Or match the binary (`pgrep -x node`) rather than a flag string. Same family as the `$status` trap above: a shell construct silently inverting a poll loop's condition. **Compounding hazard:** don't pair such a wait with a file guard on a worktree that may be pruned (`until [ -s test-debug.tap ] && ! pgrep …`) — the hourly worktree-orphan-prune deletes the file's directory, so that clause can never become true either, and the loop ends up immortal for two independent reasons at once.
- **A `$VAR` inside a single-quoted heredoc (`<<'EOF'`) stays literal — by design**: the skill templates (`hydra-dev`, `hydra-discover`, `hydra-research`, …) write PR bodies with a *single-quoted* delimiter (`gh pr create --body-file /dev/stdin <<'EOF' … EOF`) **on purpose** — quoting the delimiter suppresses ALL `$var` / `$(...)` expansion in the body as a shell-injection-safety measure. So `$CYCLE_ID` (or any branch-name var) inside that body lands as the literal text `$CYCLE_ID`, not its value (bit a retro/PR-create cycle). This is NOT a subshell-scoping issue — the var is perfectly in scope; the quoted delimiter is deliberately refusing to expand it. **Fix:** pass the value into the body literally — inline the already-resolved string, or build the body with `printf` / `jq --arg name "$CYCLE_ID" …` and feed *that* into the heredoc. **Do NOT "fix" this by switching to an unquoted `<<EOF`** — that re-enables `$var`/`$(...)` expansion and reintroduces the exact shell-injection vulnerability the single-quoting exists to prevent.
- **Single-file test run: prefer `npm run test:file -- test/<name>.test.mts`**: it wraps the same `--experimental-strip-types --test --test-force-exit` runner *and* routes through `scripts/test/redis-db-launch.mjs`, so a one-file run gets the same per-run Redis DB isolation as `npm test` — a bare `node --test …` skips that and re-exposes the cross-run keyspace-wipe flake class (#1676). It also accepts several files. It is additionally the ONLY single-file path available to a fenced GLM drainer session, whose allow-list deliberately grants `npm run:*` but never bare `node`/`npx` (a general interpreter would defeat the credential fence — see `config/glm/drainer-settings.json`). The raw form below still works when you need to hand-tune runner flags. **Never `--import tsx`**: `node --import tsx --test …` fails `ERR_MODULE_NOT_FOUND: Cannot find package 'tsx'` inside `.claude/worktrees/*` and `/dev/shm` worktrees, because `tsx` is a global install absent from the worktree's `node_modules`. (`npx tsx -e` still works — it resolves the global bin; only the `--import tsx` loader hook trips. **Caveat:** `npx tsx -e` transpiles to CJS, so a *top-level* `await` fails `ERR: Top-level await is currently not supported with the "cjs" output format` — wrap async work in an IIFE or a `.then()` chain, e.g. `(async () => { … process.exit(0); })().catch(e => { console.error(e); process.exit(1); });`. The retro/recurrence Redis shims in this repo already use that pattern.)
- **`--experimental-strip-types` rejects TS constructor parameter properties**: the `npm test` runner (`node --experimental-strip-types`) throws `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` on `constructor(private readonly x: T)` — strip-types does type *erasure* only, not the field-emitting transform that parameter properties need. `tsc`/`typecheck` **pass** (they run the full transform), so the break surfaces only at test time, and the buffered `npm test` footer hides the SyntaxError (re-run one file with `node --experimental-strip-types --test --test-force-exit test/<name>.test.mts` to see it). **Fix:** in any `src/` class exercised by a test, declare fields explicitly and assign in the constructor body — never a parameter property in the signature. Tell hydra-dev dispatches this when they add classes. (Same strip-types family as the single-file-test-run pitfall above; bit #2228/PR #2233.)
- **`/dev/shm` worktrees have no `node_modules`** — symlink immediately after `git worktree add`: worktrees under `~/hydra/.claude/worktrees/` find `node_modules` through Node's upward directory walk (ancestor `/home/gabe/hydra/node_modules`), but a `/dev/shm/hydra-worktrees/` worktree has no such ancestor — `npm test` / `npm run typecheck` / `npx tsx` fail with `ERR_MODULE_NOT_FOUND` (~128 test mis-fails that look like code regressions but aren't). Fix: `ln -sfn /home/gabe/hydra/node_modules "$WT/node_modules"` right after worktree creation. Two follow-on hazards: (a) `git worktree move` does NOT carry the symlink — re-create it after any move; (b) `.gitignore`'s `node_modules/` trailing-slash pattern matches directories not symlinks, so `git add -A` stages the symlink as a tracked file — always run `git reset -q -- node_modules` before committing. **This symlink fix is `~/hydra` (orchestrator) only — never apply it to a hydra-betting (Target) worktree.** A `/dev/shm` hydra-betting worktree symlinked straight at `/home/gabe/hydra-betting/web/node_modules` was exactly the 2026-08-19 incident (issue #4175): a destructive install step inside the worktree reached back through the link and wiped the main checkout's real `node_modules`, taking down six money-critical Target services for ~70 minutes. The structural fix (issue #4177) is different for hydra-betting: `hydra-target-build`'s Step 0.6 now creates `$TARGET_WT` nested under `~/hydra-betting/web/.worktrees/<cycle-id>` — NOT `/dev/shm` — so the SAME upward-walk mechanism this bullet describes finds the real `~/hydra-betting/web/node_modules` as an ancestor with no symlink at all (and no per-worktree `npm ci` either). The walk is safe because it is a resolver *read*; a destructive `rm -rf node_modules/` inside the worktree only ever targets a *local* path, and since neither an install nor a symlink ever creates one there, it has nothing to destroy.
- **`npm test` buffers the reporter — a `not ok` failure shows the count, not the failing test name**: the default runner streams a TAP summary, so a red run tells you *how many* failed without naming *which*. Don't grep the buffered stdout — re-run `npm run test:debug`, which adds a `--test-reporter=tap --test-reporter-destination=test-debug.tap` sink (alongside `--test-concurrency=1`); then read the `not ok` lines (and their `# Subtest:` names) out of `test-debug.tap`. That is the fast path from "something failed" to the exact `test/<name>.test.mts` + subtest to fix.
- **A `SUITE-COUNT GATE FAILED` block means the RESULT STREAM was truncated, NOT that tests were skipped — your verification still held (#4020, #4137)**: `--test-force-exit` is required (without it the suite wedges — measured: 1 of ~1,900 top-level entries in 25 minutes, because a child with a long-lived ioredis handle never exits and `--test-concurrency=1` then blocks behind it). Its cost is that the PARENT `process.exit()`s before it has finished draining the child's per-test reporter events, so the TAP footer under-reports. **The tests themselves run to completion.** Measured directly (#4137): a 10-suite/60-test file wrote an execution marker from inside every `test()` body — all 60 markers appeared on every run while TAP reported as few as 30. And a deliberately-failed assertion planted in the LAST (most-truncated) suite exited 1 with `# fail 1` on **27 of 27** runs across a synthetic file and `test/health-diagnostics.test.mts`. So a shortfall is a **reporting artifact**: never treat it as "part of the suite didn't verify", and never let it justify weakening a gate. What the gate genuinely still catches is a glob/runner-config change that drops whole FILES. Mechanically: `scripts/test/redis-db-launch.mjs` streams a per-entry capture via `scripts/test/suite-count-check.mjs`'s reporter mode and compares it against `test/fixtures/suite-count-baseline.json` (a static source-code count, immune to the race) after the child exits, with up to 2 isolated single-file retries to absorb jitter. THREE verdicts to tell apart. (1) `SUITE-COUNT GATE FAILED` — a PARTIAL shortfall: the file was measured and came up short, which is the truncation artifact and is **advisory**. (2) `SUITE-COUNT GATE INCONCLUSIVE` (#4137) — the retry never completed, so nothing was measured; regenerating the baseline here is exactly wrong, it would lower the floor on an unmeasured file. (3) `SUITE-COUNT GATE FAILED — FILE NEVER RAN` (#4141) — a baselined, in-run file that produced ZERO entries; reported separately because "observed 0" reads differently from a partial shortfall, but **also advisory**. #4141 briefly made this one blocking, on the argument that truncation drops a *tail* and therefore cannot zero a file that ran (a fully-`{skip:true}` file still emits one entry per top-level registration, since node:test reports a skipped test as `test:pass`). **That argument is wrong and production falsified it within hours**: `test/design-concept-reconcile-check.test.mts` reported `expected 2, observed 0` on a PR whose whole diff was a workflow comment plus one test file — the premise confused a per-FILE tail with the RUN's event-stream tail, and a 2-entry file fits entirely inside the undrained window. It also could never have caught its motivating case, because `npm test` passes a **shell-expanded** `test/*.test.mts`: a glob change that drops files drops them from `testFiles` too, and `compareCapture` only inspects files present in `testFiles`. **So ALL THREE verdicts are advisory and nothing sets `SUITE_COUNT_GATE_BLOCKING`** — `isGateBlocking()` defaults to false, so the required `test` job can never be reddened by any of them. The `suite-count-check.yml` workflow that used to set it was deleted in #4133: it re-ran the ENTIRE suite a second time on every PR (484 runner-minutes across 22 merged PRs, against `ci.yml`'s own 498) purely to obtain a blocking exit code, while the detection itself already runs inside the ordinary `npm test`. Because the truncation is inherent to `--test-force-exit`, **no** verdict here can be promoted to blocking while that flag is on, regardless of how many clean runs accumulate — #4062 closed without changing that, the drop simply moved to other files, and #4141's attempt to promote just the zero-entry case failed for the same underlying reason. If a file's top-level count genuinely changed, regenerate the baseline with `node scripts/test/suite-count-check.mjs --update-baseline` in the same PR (same ratchet convention as `test/fixtures/adr-area-baseline.json`); nothing forces that regeneration today, so new test files can sit outside the gate entirely.
- **Don't add new tests by nesting them inside an existing `describe` that owns a shared-Redis `after()` teardown**: a `describe`-block's `after()` hook (e.g. `test/backlog.test.mts` line ~65, which `redis.disconnect()`s the shared connection) fires when *that* suite finishes — but `node:test` runs sibling top-level suites afterward, so any **other** top-level suite that reuses the same Redis seam then runs against a torn-down connection and flakes. When you add tests that touch a shared Redis adapter, add them as a **new top-level `describe` with its own `before`/`after` lifecycle** (or reuse the suite that already owns that teardown) — never as a nested child that piggybacks on a sibling's teardown timing. (Retro-recurring; distinct from the documented "trust CI on worktree-shared-Redis flakes" coping note — this is the authoring rule that prevents the flake.)
- **Use `beforeEach`, not `before`, to reset state a test mutates across cases** — a `before()` hook runs **once** for the whole suite, so a test that mutates shared state (a Redis-backed backlog, an in-memory store, a fuzzy-dedup seed set) leaks that state into the *next* sibling test in the same suite and the two flake against each other (bit `test/backlog-move-api.test.mts`: the fuzzy-dedup seeds from one case contaminated the next until a `beforeEach` cleanup was added). The rule: if a case writes to a store that a sibling case reads, the cleanup/seed belongs in **`beforeEach`** (fresh per case); reserve `before`/`after` for *suite-lifetime* setup (open/close the connection). This is distinct from the nested-suite-shared-teardown note above — that one is about *suite ordering*; this one is about *per-case isolation within one suite*. (Retro-recurring.)
- **Friction cue fragmentation defeats auto-escalation — use the canonical `worktree-write-fence-desync` cue for ALL write-fence/anchor failures**: the five historical cue spellings (`worktree-write-fence-blocks-entered-worktree`, `edit-tool-ghost-writes-to-main-checkout-not-worktree`, `edit-resolved-to-main-checkout-needs-worktree-path`, `enterworktree-pinned-agent-write-fence-mismatch`, `enterworktree-anchor-desync-blocks-write-tool`) accumulated ~135 hits without crossing the auto-escalation threshold because they fragmented across lexically-distinct cues. The explicit alias table in `src/pattern-memory/escalation.ts` (`CUE_ALIAS_TABLE`) now maps all five to `worktree-write-fence-desync` at the `recordPattern` ingestion point. When emitting friction about a worktree write-fence failure, use `worktree-write-fence-desync` directly — it is the canonical cue the pattern store keys on. When adding a NEW high-recurrence friction cluster that the fuzzy-match algorithm (0.6 overlap threshold in `cue-matcher.ts`) doesn't naturally consolidate, add it to `CUE_ALIAS_TABLE` in `escalation.ts` (issue #2527).
- **When you REMOVE behavior, first flip the tests that *assert the old behavior* to assert the new invariant — then add the regression test** — existing test cases routinely pin the exact behavior you are about to delete (a fallback path, a default, a now-forbidden lane transition). If you add the new regression test *first* and run the suite, the pre-existing cases fail and look like *your* breakage, so you either chase a phantom regression or (worse) "fix" the new code to keep the old behavior alive. The order that avoids the trap: (1) rewrite each existing case that asserts the about-to-be-removed behavior so it asserts the *new* invariant (e.g. a scan-fallback test becomes a `not-found-without-scan` test), (2) watch them go red against unchanged code (confirming they really pinned the old behavior), (3) make the code change green them, (4) only then add the new regression test for the new path. Bit `test/backlog-title-index.test.mts` (two scan-fallback cases had to be rewritten to assert not-found-without-scan before the by-title-index regression could be added). (Retro-recurring.)
- **In `~/hydra-betting/web`, `npm test` is a count-gate + 3 sentinels, NOT the full suite — the real suite is `test:raw`**: the Target's `web/package.json` `test` script is `MIN_PASSING_TESTS=2301 node ../scripts/verify-test-count.js && node --test …three jit-verified-sports-pairs *.mts files`. So a `npm test` run that prints "X tests passed" is reporting (a) the count-guard's *internal* vitest tally against a frozen floor plus (b) three named sentinel files — it is **not** executing the project's vitest suite as a pass/fail gate. An agent that reads that footer as "the full suite is green" can ship a change that breaks untested betting modules. The actual full suite is **`npm run test:raw`** (`vitest run --config ./vitest.config.ts --dir ./src`). When verifying a Target change in `~/hydra-betting/web`, run `test:raw` (and let CI's vitest job be the gate) — treat bare `npm test` there as a *count ratchet*, not suite verification. (This is `~/hydra-betting/web` only; the Orchestrator's `npm test` IS the full node:test suite. Retro-recurring across hydra-target-build.)
- **`design-concept-reconcile` reads the PR body from the webhook payload captured AT PUSH TIME, not live state — order `git push` and `gh pr edit` so the LAST push happens after the body is already correct**: fixing quote-mismatch / unparseable-assertion violations by editing the PR body via `gh pr edit` alone, then re-running the failed check, replays the ORIGINAL (broken) body every time — the gate's own error message says "push a commit" but doesn't warn that `push` *before* `gh pr edit` in the same turn still captures the stale body, because the `synchronize` webhook fires (and CI starts) off the push, independent of a body edit that lands microseconds later. Bit twice in one PR (#4242): fixing the body via `gh pr edit` and pushing an unrelated follow-up commit in the same breath still replayed the pre-edit body, because the push landed first. Fix: after any `gh pr edit` that corrects the reconciliation section, push ONE MORE commit (even a trivial one, e.g. a comment/doc touch) so the triggering `synchronize` event's payload snapshot carries the corrected body.

## Agent skills

- **One-lineage Pocock spine** (ADR-0030, epic #3419) — the orchestrator lifecycle runs on **one autonomy-capable skill lineage, two modes** (interactive for the operator, AFK for autopilot), not the old `hydra-prd`/`hydra-dev`/`hydra-qa` fork triplet.
